# Disclosed v1.0.0 issue: tie-decided periods and the numba cache (v1.0.0 unchanged)

Found 2026-11-10 during the cross-host gate (`docs/host_gate/README.md`). v1.0.0 products are not modified.

## What happens

The v1.0.0 search takes the best peak with a plain argmax. For a sizeable fraction of stars several (P, D) grid
points give the same scan statistic to within ~1e-15 (typically two or three transits that several nearby periods
fold onto the same in-transit points, at P of several days up to half the baseline). Which of those is reported
then depends on last-bit arithmetic: wotan's biweight kernels are numba-compiled with `fastmath=True, cache=True`,
and a freshly JIT-compiled kernel and the copy loaded from the on-disk cache can differ in the last bit.

## Measured exposure (`python -m exosearch.host_gate v10check`)

200 stored v1.0.0 rows (S105 real search, seeded sample) recomputed on the coordinator with per-process empty numba
caches (fresh JIT):

* **P differs in the last bit in 26 of 200 rows (13%)**: |ΔP| ≤ 1.8e-15 d (median 1.8e-15 d), the same grid
  point; D and T0 are identical in all 26 and S differs by at most 3.6e-15 (no row beyond 1e-6). *Correction
  (2026-11-10 22:00 PST): an earlier version of this note described these 26 as (P, D) flips; none moved to another
  grid point, plateau member or peak.* On one host, fresh vs cached kernels change only the last bit of P.
* Re-running 12 of those 26 with the normal (cached) kernels reproduces the stored rows exactly (12/12), so the
  stored rows were produced by cached kernels.
* Peak changes between members of a tie band were seen only across architectures (arm64 vs x86_64, 6 of 200 S70
  stars, from the arm64 period grid; `docs/host_gate/README.md`). No v1.0.0 row was computed on arm64.
* In the cross-host dry run with the registered tie-break, 25 of 200 S70 stars (12.5%) had more than one grid point
  inside |S_i − S_max| ≤ 1e-9·S_max (up to 38): for those stars the period was decided by arithmetic, not data.

## Plateau framing (tie-break amendment 1, `docs/host_gate/plateau_report.json`)

The in-band grid points are mostly **contiguous plateaus**, not separate peaks: with one or two transits, a range of
adjacent trial periods folds the same in-transit cadences together and gives the same S to the last bit. On the 200
S105 rows above (fixed-grid search): 162 single grid points, 27 stars (13.5%) with one plateau of 2–35 grid steps,
11 (5.5%) with disjoint in-band peaks; 27 of the 29 plateaus wider than one step are at n_tr ≤ 2. **All 26
cached-vs-fresh differences stay inside one plateau, and every shift is far below the plateau half-width**
(|ΔP| ≤ 1.8e-15 d against half-widths of 4.8e-5 to 0.064 d; ratio ≤ 5e-12). For a tied star the v1.0.0 period is
the plateau point picked by argmax. The plateau half-width (**grid-degeneracy half-width**, `P_grid_halfwidth`;
median 0.0075 d, max 0.17 d over the plateau stars, median 0.0014 d over all 200 rows) measures how far along the
trial-period grid the statistic is exactly degenerate. It is **not a period error**: it does not include the
photometric uncertainty, and with n_tr ≤ 2 the true period may be P/n (n = 2, 3, …), so those periods are flagged
`period_ambiguous`. v1.1 reports the plateau centre with `P_grid_halfwidth` (`docs/preregistration/tie_break.md`,
amendment 1), and both columns are now in the candidate tables and exports (`analysis/SCHEMA.md`).

## Consequences

* **S, S_exact, S*, the null tails and the completeness by expected S are unaffected** (they use S only).
* Reported periods/durations and T0 of tied stars are the argmax member of the tie band, a deterministic choice
  on x86_64 with the stored environment; within a host the cache state changes only the last bit of P. Period-based
  steps (injection matching within 1% in P, common-period flag, TOI period match, odd/even epochs) depend on that
  choice for tied stars; the bands span up to ~2% in P. Not corrected in v1.0.0; see the injection recheck below.

## Injection recheck with fresh kernels (`docs/host_gate/injection_recheck.json`, `python -m exosearch.inject_recheck`)

310 stored v1.0.0 S70 injection rows (300 seeded at random, seed 20261110, plus every stored row on a gate star
with a tie, 300 hosts) recomputed with the unchanged v1.0.0 code and per-process empty numba caches (fresh JIT), on an
x86_64 worker (bit-identical to the coordinator in the gate). 22 rows had more than one grid point in the tie band
(20 with a plateau wider than one step, 10 with disjoint in-band peaks). Recovered period changed in 41 rows and T0
in 45, all in the last bit (|ΔP/P| ≤ 2.3e-16, |ΔT0| ≤ 4.6e-13 d); D unchanged; |ΔS| ≤ 2.3e-13, |ΔS_exact| ≤ 5.8e-10.
**No row changed matched, detected, passed_all, failed checks, or the interim recovered (matched and S_exact ≥ S*
11.07) / vetted status: completeness is unaffected.**

## Provenance: '-dirty' git stamps (`docs/host_gate/dirty_stamps_s105.json`, `python -m exosearch.dirty_stamps`)

v1.0.0 stamps `git_hash` per row at write time and appends `-dirty` when `git diff -- exoplanet_search/exosearch` is
non-empty, i.e. when any file under `exosearch/` was uncommitted, whether or not the search used it. At the time of
this check 11,322 v1.0.0 S105 rows carry 2,610 `-dirty` stamps under 20 distinct base hashes. `pipeline_version` and
`config_hash` (`80ffc7f29943`) are constant.

Reconstruction. The stamp says nothing about the code that ran: the continuous search loads its code once when the
search pool starts (the per-star workers persist for the whole sector). The service log shows two pool starts for S105:

| pool start (PST) | HEAD at start | tree at start (first row's stamp) | rows | uncommitted edits at start |
|---|---|---|---|---|
| 17:10:51 | 37074a00 (data commit) | dirty | 378 (273 stamped dirty, 105 stamped clean after the commit) | the v1.0.0 freeze itself, committed 4 s after the pool's last row as 83eac4dd (17:13:15): bls, lightcurve, task, vet, store, version + non-search modules — **search/vetting path** |
| 17:14:25 | 83eac4dd | clean | 10,944 (2,337 stamped dirty) | none; the pool runs the committed 83eac4dd code |

For each later dirty hash, the uncommitted edits (the exosearch/ files of the next commit) were analysis- and
interim-layer modules (reliability, interim, export, depth_audit, stat_options, cut_sensitivity, nulldiag, quality,
whitenoise, ffi_check, labels, stellar, batch, host_gate, worker_guard; the deepvet change is in the deep-vetting
Gaia query, not in the per-row search). None touches the per-star search/vetting closure of `run_search.py`
(run_search, catalogs, config, plots, store, targets, vet, task, bls, lightcurve, version), and no commit since
83eac4dd has changed those files; in any case the 17:14:25 pool did not reload code. So the 2,337 dirty stamps of the
second pool are cosmetic.

**Flagged:** the 378 rows of the 17:10:51 pool (they ran a working-tree state that became 83eac4dd, but which exact
state cannot be proven from git). Queued for a re-run with the committed v1.0.0 code in
`configs/rerun_queue_v1.0_s105_dirty.txt` — **not launched**. v1.0.0 products are not modified.

**v1.1 rule:** workers refuse to start on a dirty tree (`exosearch/worker_guard.py`, tracked files must match HEAD;
used by `host_gate run`, to be called by every v1.1 entry point), and the stamp moves from per-row write time to
pool start.
