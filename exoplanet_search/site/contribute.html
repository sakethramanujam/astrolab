Run it yourself, or lend us compute

Every star is an independent job, so the search scales by simply adding machines: a laptop CPU, an old NVIDIA card or an Apple Silicon Mac. Here's how to run the pipeline on your own and how a worker joins a shared scheduler.

Run a sector on your own machine

# Python 3.12, ~2 GB disk per 1,000 stars
git clone <repo-url> astro-compute-lab && cd astro-compute-lab/exoplanet_search
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
export EXO_DATA_ROOT=$PWD/data            # where light curves and results go
.venv/bin/python -m pytest -q tests        # injection-recovery and end-to-end checks

# 500 random stars from sector 70 on 4 cores, low priority
nice -n 19 .venv/bin/python run_search.py --sector 70 --n-targets 500 --workers 4
.venv/bin/python -m exosearch.export       # writes site/data/progress.json + plots
python3 -m http.server -d site 8000        # open http://localhost:8000

Results land in $EXO_DATA_ROOT/results/exosearch.sqlite (one row per star) and a Parquet export. Re-running skips stars already searched; --n-targets 0 does the whole sector; python -m exosearch.sectorqueue next --count 3 tells you what's next.

How the distributed search works

Coordinator

Downloads light curves, runs a Dask scheduler, stores results and publishes this site.

One star = one task

Tasks are handed to whichever worker is free; slow or fast machines just take fewer or more stars.

Resource tags pick the engine

A worker started with --resources GPU=1 runs BLS with CuPy; MLX=1 with Apple MLX; untagged workers use astropy on CPU.

Same answers

Every engine's best period is re-scored on CPU with the same vetting, so results are comparable.

NVIDIA GPU worker

Tested target: GTX 1050 Ti (Pascal, sm_61, 4 GB). Needs an NVIDIA driver ≥ 525 and the CUDA 12 runtime.

pip install -r requirements.txt -r requirements-cuda.txt   # cupy-cuda12x
nvidia-smi
pytest -q tests/test_bls_vector.py                         # CUDA vs numpy check
SCHEDULER=tcp://<scheduler-host>:8786 scripts/start_worker_cuda.sh

One process with GPU=1, so the card is never shared by two tasks. The CUDA path is new: validate it with the test first.

Apple Silicon worker (MLX)

brew install python@3.12
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-mlx.txt   # mlx
.venv/bin/python -c "import mlx.core as mx; print(mx.default_device())"
pytest -q tests/test_bls_vector.py
SCHEDULER=tcp://<scheduler-host>:8786 scripts/start_worker_mlx.sh

MLX runs BLS on the Mac's GPU in float32. Add scripts/start_worker_cpu.sh alongside to use the CPU cores too.

Joining a scheduler safely

  • Dask's scheduler has no authentication. Only expose it on a private LAN or a mesh VPN such as Tailscale, never on the public internet.
  • Use the same Python minor version and the same dask/distributed versions as the coordinator.
  • Workers without the shared disk download light curves into their own EXO_DATA_ROOT; nothing else is needed.
  • Run workers with nice -n 19 (the scripts do) so they stay out of the way of everything else on the machine.

Ways to help without compute

Look through the needs-review list, open a diagnostic sheet, and check the star on ExoFOP and in other sectors. Spotted an eclipsing binary or a systematic we missed? That feedback improves the screens for everyone.
